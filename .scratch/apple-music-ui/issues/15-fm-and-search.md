# 15: 广播与搜索

**Blocked by:** 04: 移动端服务层, 05: 移动端播放引擎, 12: 模型可读界面与 refs

**Status:** done

## 现状与缺口

- spec 的 **D3** 把「广播与搜索的实装」列为 Deferred，理由是：「广播是持续流式播放，依赖播放引擎的长队列与续播语义；搜索需要分页与结果详情页，两者都超出本轮四屏的范围。」
- 当时给出的占位实现是 `www/mobile/views/coming.js`：`M.views.fm` 与 `M.views.search` 都是同一个 `coming()` 工厂产出的占位页，点进去只有一句「「广播」将在后续版本开放」。
- **具体缺口（服务层）**：`www/mobile/core/service.js` 没有 FM 与搜索的任何通道 —— `personalFM` / `fmTrash` / `search` / `searchSuggest` / `searchDefaultKeyword` 在内核里都有（`www/kumone/lib/api.js:151`、`:154`、`:195`、`:200`、`:203`），但移动端侧无人调用。
- **具体缺口（动作白名单）**：动作白名单只有 `click` / `scroll` / `focus`（`www/mobile/core/snapshot.js` 的 `ACTIONS`）。搜索页的核心动作是「往输入框里写字」，**模型没有对应的动作**，于是搜索页对模型是不可驱动的 —— 一张人能用、模型用不了的页面等于半成品。
- **具体缺口（归一化）**：FM 接口 `/v1/radio/get` 返回的是**旧版字段**（`artists` / `album` / `duration`），而搜索的四个类型返回的是新版字段（`ar` / `al` / `dt`）。共享归一化层两边都吃（ticket 03），但没人把这两条路径接起来。
- **具体缺口（语义）**：搜索输入框如果没有稳定的无障碍名，模型在快照里就找不到它；类型切换按钮如果没有名字，模型就不知道自己能搜什么。

## 要求

- 让底部导航的「广播」与「搜索」不再是占位页，各有一个真实可用的视图。
- 让广播页能取到私人 FM 的曲目、显示当前曲目与封面，并提供「下一首」与「不喜欢」两个动作；「不喜欢」要真的调 `fmTrash`。
- 让广播页在未登录时给出登录引导（与资料库同一条路径），而不是空页面或一句「将在后续版本开放」。
- 让搜索页具备：搜索输入框、搜索按钮、类型切换（单曲 / 专辑 / 歌手 / 歌单）、输入联想、结果区。
- 让联想里的单曲作为新的搜索词，专辑 / 歌手 / 歌单直接进入对应详情页（与上游语义一致）。
- 让搜索结果按类型用合适的方式呈现：单曲用可播的曲目行，专辑 / 歌手 / 歌单用封面卡网格；每个结果都带语义名与 ref。
- **让模型能驱动搜索**：在动作白名单里增加 `fill`（往可填写的输入框写字并触发 `input` / `change`），白名单仍然是硬的 —— 白名单外的动作、以及对不可填写元素调用 `fill`，都必须返回 `KUMONE_UNSUPPORTED` 并列出可用动作。
- 让知识包 manifest 声明的动作白名单与实现保持一致，并在校验器里加一条对齐检查，防止两边漂移。
- 为两页各写一组自测：服务层（Node）与视图（浏览器探针），并接入 `package.json` 的 npm script。

## 明确不做什么

- 不做搜索分页与「加载更多」：本轮只做首屏结果（与主页同一原则）。
- 不做搜索结果页的独立详情体系：结果点进去复用现有的歌单 / 歌手 / 专辑详情页。
- 不做 FM 的「续播」语义（播完自动要下一首）与插播队列；本轮只做「下一首」按钮。
- 不把手势（滑动切歌、滑动返回）纳入动作白名单（spec 的 D2 仍然是 Deferred）。
- 不做逐字歌词页（spec 的 D1 仍然是 Deferred）。

## Comments

这一页是 spec 里 D3 明确 Deferred 的。用户在本轮把它拉回来做了，所以实现时多了一条 spec 没写的要求：**模型侧也得能用**。

### 一个必要的契约变更：动作白名单加 `fill`

搜索页的核心动作是写字，而白名单里没有能写字的动作。三个选项：

1. 只让人能用，模型用不了 → 搜索页对模型是死的，与「双模态」这个基线矛盾。
2. 让模型直接改 DOM → ADR-0003 明确禁止。
3. **给白名单加一个 `fill` 动作** → 语义明确、有边界（只能作用于可填写元素）、能被错误契约覆盖。

选了 3。`fill` 的边界是：
- 只对 `input`（text / search / email / url / tel / password / number）、`textarea`、可编辑元素生效；
- 对 `<button>` 之类不生效 —— 注意 `<button>` **也有 `value` 属性**，不能用 `'value' in el` 当判据（踩过）；
- 失败返回 `KUMONE_UNSUPPORTED`，消息里列出可用动作。

契约变更同步到了 5 个地方：`AGENTS.md`、`README.md`、`spec.md`（R51 / M5 / Deferred 描述）、`requirements/模型可读界面.md`、知识包 `manifest.json`。

### 白名单漂移的刹车

知识包要「可独立拷走」，所以它自持一份动作白名单声明。代价是可能漂移 —— 所以在 `test/validate-learnings.mjs` 里加了一条对齐检查（和码表对齐同一思路）：manifest 声明的必须与 `snapshot.js` 的 `ACTIONS` 一致。`npm run test:actions:prove` 做反向自证：故意改漂移 → 校验器必须失败 → 自动还原。

### 踩过的坑

- **`view.type` 不是搜索类型**：搜索页一开始写成 `var type = (view && view.type) || 1`，而 `view.type` 是**视图类型**（`'search'`），于是 type 变成了字符串 `'search'`，接口返回的是歌单而不是单曲。搜索类型要用自己的字段名（`view.searchType`）。
- **`<button>` 也有 `value`**：`fill` 的可填写性判断最初用 `'value' in el`，结果对按钮也判定为「可填写」，于是往按钮上 `fill` 不会报错。判断必须看标签名与 input type。
