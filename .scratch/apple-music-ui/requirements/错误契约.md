# 错误契约

> 载体：`.scratch/apple-music-ui/requirements/错误契约.md`
> 决策依据：`docs/adr/0003-双模态界面与ego视觉语言.md`（§5 错误按「下一步该干什么」分类 / §6 错误码是契约、措辞是实现）
> 理论来源：`docs/ego-lite-UI设计理论.md`（L4 反馈层）
> 对应 ticket：`.scratch/apple-music-ui/issues/13-error-contract-and-stable-codes.md`

## 1. 现状与缺口

- 契约的**骨架已经写好**：`www/mobile/core/errors.js` 有 14 个稳定码的码表 `CODES`（`:15-29`）、契约错误构造 `make()`（`:36-52`）、五要素消息拼装 `compose()`（`:54-65`）、内核错误映射 `fromKernel()`（`:71-132`）、可重试判定 `retryable()`（`:135-137`）。分类按「下一步该干什么」而非按成因：
  - `transient`（可原地重试）：`KUMONE_NETWORK`（`:18`）、`KUMONE_TIMEOUT`（`:19`）、`KUMONE_DECODE_FAILED`（`:20`）、`KUMONE_RATE_LIMITED`（`:21`）
  - `permanent`（须换策略）：`KUMONE_NEED_LOGIN`（`:16`）、`KUMONE_AUTH_EXPIRED`（`:17`）、`KUMONE_EMPTY_RESULT`（`:22`）、`KUMONE_NOT_FOUND`（`:23`）、`KUMONE_UNBLOCK_FAILED`（`:24`）、`KUMONE_STALE_REF`（`:25`）、`KUMONE_AMBIGUOUS_TARGET`（`:26`）、`KUMONE_NO_ACTIVE_PLAYER`（`:27`）、`KUMONE_UNSUPPORTED`（`:28`）
- 已有产出点：`www/mobile/core/snapshot.js:45` 产出 `KUMONE_STALE_REF`，`:243` 产出 `KUMONE_UNSUPPORTED`；知识包侧另有 `KUMONE_EMPTY_RESULT` / `KUMONE_NOT_FOUND` / `KUMONE_AMBIGUOUS_TARGET` 三个产出点（`www/mobile/learnings/netease/tools/playlist.js:43` / `:68` / `:78`）。
- **缺口一（已部分收口）**：契约**已有调用方** —— `www/mobile/core/service.js` 的 `call()` 是唯一翻译点，视图层不再直接碰内核错误。**但界面层仍未消费**：`www/mobile/views/home.js` 与 `library.js` 对 `M.errors` 的引用数仍为 0 —— `KUMONE_NEED_LOGIN` 已经能带着「扫码登录后重试」的下一步动作走到界面边上，但界面上还无处可扫码（ticket 06/08/10）。
- ~~**缺口二：`business` kind 被误分类成 transient。**~~ **已于本轮收口**：`fromKernel()` 新增 `kind === 'business'` 分支，产出新增的 `KUMONE_BUSINESS_REJECTED`（permanent），`next` 明说「不要重试：换一个请求参数或换一个数据入口」；不再兜底成 `KUMONE_NETWORK`（transient）导致无限重试。回归断言见 `test/service.test.mjs`。
- **缺口三：错误码表现在有三份。** 权威表在 `www/mobile/core/errors.js:15-29`（14 码）；知识包 `www/mobile/learnings/netease/tools/locator.js:35-41` 自持一份 5 码子集 `TITLES`（注释 `:33-34` 自称「与 core/errors.js 同构」）；`www/mobile/learnings/netease/manifest.json:39-43` 又用 `errorCodes` 写了第三份 5 码说明。**没有任何校验器把三者对齐** —— 码表漂移是已经发生的事实而不是风险。
- **缺口四：五要素没有强制校验，「缺省」与「缺失」分不开。** `compose()` 的注释写明「缺省的部分不出现，不制造噪音」（`errors.js:54`），`:56-64` 只在字段非空时追加对应行。因此一条只带 `next` 的错误是合法的，但 ADR-0003 §6 要求消息含五要素（期望签名 / 当前状态 / 候选 / 阻塞原因 / 下一步动作）。目前**无法判断一条错误消息是否合格** —— 尤其 `candidates` 只在歧义类错误里才有意义（`:59-61` 最多列 3 个），强制所有错误都带候选既无意义也会制造噪音。
- **缺口五：码表没有回归保护。** `test/guard-design.mjs:78-93` 只检查**每个码都声明了 `kind`**，不检查码的数量、集合、语义，也不检查与知识包的两份副本是否一致 —— 删一个码、或把 `KUMONE_NETWORK` 的 `kind` 从 transient 改成 permanent，都不会被现有闸门发现。
- **缺口六：无法证明调用方是「按码分支」。** ADR-0003 §6 明确「按码分支，不按文案分支」，但仓库里**没有任何断言**能检查调用方看的是 `err.code` 而不是 `err.message`。现有的 `test/model-actions.mjs` 验证的是动作层返回契约错误（码正确），不是「调用方按码分支」。
- ~~**缺口七：两个码尚无产出点。**~~ **已于本轮收口**：`KUMONE_NO_ACTIVE_PLAYER` 由 `www/mobile/core/player.js` 在「队列为空却要播放 / 取不到可播地址」时产出；`KUMONE_UNBLOCK_FAILED` 由服务端 `unblock()` 与引擎的解锁兜底失败路径产出。

## 2. 要求

- 让 14 个 `KUMONE_*` 错误码成为**唯一权威**的持久契约（权威源 `www/mobile/core/errors.js:15-29`）：码的含义与 `kind` 分类不可随意更改；新增码必须同步更新码表、自测与文档三处（四处同步契约见 ADR-0003 §10）。
- 让知识包的两份副本（`www/mobile/learnings/netease/tools/locator.js:35-41` 的 `TITLES`、`www/mobile/learnings/netease/manifest.json:39-43` 的 `errorCodes`）由校验器与 `www/mobile/core/errors.js:15-29` **逐码对齐**：码集合、`kind`、标题三者一致才算通过；不允许知识包自持一份「同构但独立」的码表。
- 让所有内核失败在进入界面层时都经 `fromKernel()` 翻译成契约错误；界面层不得自造错误结构。
- 让 `fromKernel()` 补齐 `business` kind 的映射，并归入 `permanent`（业务失败换策略重试没有意义）；同时确认内核 kind 与 HTTP 状态的优先级不冲突（`errors.js:71-76` 目前先看 `kind` 再看 `status`，映射规则要在补齐后重新核一遍）。
- 让错误消息的**五要素**成为可校验的契约：按错误类别规定必备要素（歧义类必须带 `candidates`，过期类必须带 `expected` 与 `next`，鉴权类必须带 `next`），缺失即不合格；不要求所有错误都塞满五段。
- 让等待循环**只对 `transient` 重试**：`permanent` 错误必须直接失败并给出「换策略」的下一步动作。
- 让调用方一律**按 `code` 分支**：`if (err.code === 'KUMONE_NEED_LOGIN')` 是唯一允许的写法；按文案分支的写法在自测里失败。
- 让 `KUMONE_AMBIGUOUS_TARGET` 在核心层也有产出路径（当前只有知识包侧 `www/mobile/learnings/netease/tools/playlist.js:78` 产出），配合 requirements/模型可读界面.md 的核心 locator。
- 让 `KUMONE_NO_ACTIVE_PLAYER` 与 `KUMONE_UNBLOCK_FAILED` 在各自的实现落地时接上（ticket 05）。
- 新增错误契约自测：14 个码的存在性与分类、**与知识包副本的一致性**、`fromKernel()` 对内核各 kind 与 HTTP 状态的映射、错误消息五要素的分类必备性、按码分支的反例检测；并接入 `package.json` 的 npm script。

## 3. 明确不做什么

- 不修改已发布码的语义或 `kind` 分类；确需调整时先改设计文档（`docs/adr/0003` 或本文件），再改实现。
- 不为每个界面场景单独发明错误码；语义上能归入既有码的，用既有码 + 不同的 `cause` 表达。
- 不用错误消息文案做程序分支；文案可漂移，码不可。
- 不在错误契约层实现具体的退避算法；本层只判定「该不该重试」。
- 不把 `KUMONE_UNSUPPORTED` 用作「功能暂未实现」的通用码 —— 那是 spec 的 Deferred（广播 / 搜索占位），与「动作不在白名单」是两件事。
- 不把知识包的码表当成「独立的一份实现」来维护；它必须是核心码表的投影。

## 4. Acceptance

- [ ] 执行错误契约自测脚本，确认 14 个码全部存在，且每个码的 `kind` 与 `www/mobile/core/errors.js` 的 `CODES` 一致（4 个 transient、10 个 permanent），全部 PASS。
- [ ] 确认校验器会**逐码比对** `www/mobile/core/errors.js:15-29` 与 `www/mobile/learnings/netease/tools/locator.js:35-41`、`www/mobile/learnings/netease/manifest.json:39-43`：在知识包里改一个标题或加一个码，确认校验**失败**并指出文件与行号（反向验证检测器有效）。
- [ ] 用假门面注入内核 `kind: 'business'` 的失败，确认产出的错误是 `permanent` 且**不是** `KUMONE_NETWORK`；确认它不会被自动重试。
- [ ] 用假门面分别注入 `needLogin` / `decoding` / HTTP 401 / HTTP 429 / timeout / 网络错误，确认分别产出 `KUMONE_NEED_LOGIN` / `KUMONE_DECODE_FAILED` / `KUMONE_AUTH_EXPIRED` / `KUMONE_RATE_LIMITED` / `KUMONE_TIMEOUT` / `KUMONE_NETWORK`，且分类与预期一致。
- [ ] 逐类检查错误消息，确认含该类**必备**要素：歧义类带 `Candidates`（`errors.js:59-61`）、过期类带 `Expected` 与 `Next`、鉴权类带 `Next`。
- [ ] 在 `www/mobile/` 全目录检索按文案分支的写法（对 `message` / `title` 做 `includes` / `indexOf` 后决定行为），确认自测报**失败**并指出文件与行号。
- [ ] **反向验证检测器**：故意把某处临时改成按文案分支，确认自测确实抓得到；改回后重新通过。
- [ ] 确认一条 `permanent` 错误进入等待循环时被**立即抛出**而不是继续轮询；一条 `transient` 错误允许重试。
- [ ] 确认 `errors.retryable()`（`www/mobile/core/errors.js:135-137`）只对 `kind === 'transient'` 返回 true。
- [ ] 确认在 `www/mobile/` 全目录不存在自造的错误结构（形如 `{ ok: false, msg: ... }` 这类绕过码表的写法）。
- [ ] 执行 `npm test` 与 `npm run test:live`，确认均保持通过。
